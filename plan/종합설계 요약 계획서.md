# DeteCam 종합설계 요약 계획서

1. **목표**: 수신기 1기를 여러 자리에 옮겨 두고 ① 여러 전자기기 가운데 Wi-Fi 카메라만 골라내고(실측 재현율 95% 이상, 오탐 5% 이하) ② 사람이 많고 반사가 있는 방에서 기존 논문 방식(DiffLoc)보다 방향 오차를 평균 3° 이상 줄이며 ③ 카메라 위치를 좁히고(시험실 밖 0.5 m 안 80%, 시험실 의심 책상 3곳 안 80%) ④ 의심 구역을 스마트폰 AR로 표시한다. 조건: 저소음, 부품 값 70만 원 미만, 재는 동안 사람이 돌아다니지 않음, PCB 외주 없음, 크기 20 cm 내외, 기기 사이 무선, 시험장 좌석 정보 미리 입력 안 함.
2. **수신기 (`DeteCam/receiver`)**: 지름 12 cm 원 위의 필름 안테나 16개를 SP16T 스위치로 번갈아 연결하고, 가운데 기준 안테나와 함께 Intel AX210 한 장으로 받는다. 안테나 케이블은 고리 면 안에서 모아 한 묶음으로 내린다(등뼈 배선). 머리가 −20° · 0° · +20°로 끄덕이고 재는 동안에는 모터를 끈다. 호스트는 Raspberry Pi CM4다. 쇼핑몰 부품을 SMA · 볼트 · 3D 프린트로 조립하며 1기 약 48~51만 원(추정)이다.
3. **소프트웨어 · AI (`DeteCam/ai`)**: 실제 기기 캡처로 학습 · 평가하는 카메라 판별, 두 수신 체인 비율과 앵커로 위상 기준 맞추기, 안테나 간섭 보정표, 벽 · 천장 반사를 계산에 넣는 지도 반영 추정, 여러 자리 지도를 합쳐 방향과 위치 내기, 믿을 만한 측정 가려내기, 자리를 더 잴지 안내하기. 새로 만든 방 16개 시뮬레이션에서 오차를 줄인 것은 구조 변경이 아니라 이 소프트웨어 절차였다(계산값).
4. **앱 (`DeteCam/app`)**: 폰 AR로 방 크기와 수신기 위치를 잡고, 수신기를 블루투스로 조종하며, 다음에 잴 자리를 안내하고, 방향 부채꼴과 의심 구역을 AR로 표시한다.
5. **서버 · DB · 클라우드 ([SPEC-001](../specs/001-server-cloud/spec.md))**: 측정은 수신기와 폰만으로 끝내고, 서버는 점검 기록 보관(Spring Boot REST API, PostgreSQL · AWS RDS), 판별 모델 · 보정표 배포(S3), 기관 관리자용 React 웹 관리 화면을 맡는다. 원본 신호와 남의 기기 주소 원본은 서버에 올리지 않는다.
6. **검증 순서**: 문서 · 데이터시트 확인 → 시뮬레이션(유리한 조건 금지 규칙, 계획서를 결과 전에 고정) → 1기분 부품으로 벤치 시험(호스트 부팅, 두 체인 CSI와 위상 안정성, 스위치, 앵커) → 고리 1기 빈 방 측정 → 교실 · 반사 많은 방에서 DiffLoc 재현 장비와 번갈아 측정 → 실제 기기 판별 평가 → AR 시연. 자세한 기준은 `docs/AGENTS.md`.
